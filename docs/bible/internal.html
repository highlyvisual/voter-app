01 · Overview

The platform on one page

What’s It To Me? is a non-partisan UK voter-information site. You give it a postcode and a few facts about your household, in bands. It shows every candidate on your ballot, in ballot-paper order and on identical pages, and quotes what each has published, with the source. Where the numbers allow, it also shows what each one winning would change for a household like yours.

The idea is Romily’s: an informed electorate makes better decisions, and the way to inform it is to connect politics to a person’s own life without telling them what to think. The site never ranks, scores, matches or recommends. It shows consequences and sources; the voter judges. The test for anything new: could a reader take it as the site preferring one candidate? If so, it is not built.

Where AI is and is not used

AI helps draft the short summaries and helps research sources; every such row records it in drafted_by, and every quotation is checked word for word against the source before it is loaded. No AI runs when a visitor uses the site: every page is built from the ledger and official data.

02 · Non-negotiables

The rules the code enforces

These came from Romily at the start (impartial, every fact attributed, no way to manipulate figures, no grounds to say the system prefers anyone) and were turned into constraints the code checks, not just intentions.

How candidates are shown

  • Every candidate gets the identical template, in ballot-paper order (alphabetical by surname). No other ordering exists anywhere.
  • No ranking, scoring, matching or recommending. Consequences are shown; the reader judges.
  • Colour is neutral. A party’s own colour appears only on that party’s own panel, and only if set in parties.colour_hex. Money figures never carry good/bad colours.
  • Photos appear only on a candidate’s own page; everywhere else it is name and party (Romily, round five).
  • Where a candidate has no record in office, the same neutral line is shown for everyone: “Has not held this office before, so there is no voting record to show.” Party positions are the layer every candidate has; a personal record is extra.

How facts are held

  • Every claim is a verbatim quotation from a named, dated, linked source. A short summary sits beneath it as a reading aid; the quotation is the record.
  • Claims live in an append-only ledger. Rows are superseded, never edited or deleted; a Postgres trigger refuses updates and deletes.
  • Corrections and withdrawals go through /review by a named maintainer and are logged publicly with the reason.
  • Publication rests on the source, not on a reviewer (Romily, 18 September 2026).
  • Households are described in bands only. Nothing a visitor enters is stored; the full postcode never leaves the lookup.

The never-build list

04 · The journey

A visit, from postcode to ballot

What happens, in order, when someone uses the site, and which page or file does each step.

  1. Postcode. The form posts to the server action in app/find/actions.ts, so the postcode never appears in a URL, log or redirect. It checks the format, asks Democracy Club’s developers API which ballots cover it (falling back to the candidates API, then to postcodes.io’s constituency), and asks postcodes.io for a rounded location. Only the outward code (for example NW1) travels on, to draw an approximate circle on the map. The full postcode is then discarded.
  2. Profile. /start asks which elections you can vote in, then household facts in bands: adults, children, housing, work, income band, age band. Student answers were added on 24 September at Romily’s request. Answers stay in the browser.
  3. Ballot. /ballot/[id] shows every candidate in ballot-paper order, with topics ordered by the profile and the reason shown, then “Explore all topics”. Each card carries the same sections, including “Stood before” and “Record in office”.
  4. Depth. From there: each candidate’s own page, a topic across all candidates, a compare grid, the office being elected, the area around the postcode, and a printable notes sheet.
  5. Practical. Deadlines, where to vote and accepted ID, from election_dates and the Electoral Commission. Then two feedback questions, kept only as daily totals.

05 · Database

The data model

One Postgres database, grouped here by job. Tables marked append-only have triggers that refuse updates and deletes. Every table has row-level security switched on (the only exception is PostGIS’s own spatial_ref_sys).

Elections

ballots (31 not archived, 34 in all): one row per ballot paper, keyed by Democracy Club’s ballot_paper_id, with level, poll date, area, GSS code, previous contest, cancelled or postponed flags.

candidates (161): name, party, verbatim statement to voters, photo and its licence, Parliament member id where matched. parties (25): Electoral Commission id, official site, optional colour. election_dates: deadlines and notice links. previous_candidacies (271), ward_history (652), leaflets (28).

Claims ledger

claims (506 rows, append-only): ballot or party, topic, tier, summary, the quote, applies_if, status, supersedes, drafted_by, precision.

sources (94): title, URL, publisher, the source’s own date, retrieval date, content hash, layer. change_log (517, append-only). verifications (append-only). View current_claims: the live set (376).

Money

receipt_grid (40,500): one row per household cell per reform set, with the household, results and the PolicyEngine version. party_funding: Electoral Commission donations, summarised per party.

Place and councils

councillors (19,273) and council_control from Open Council Data. council_tax_2026 (319), deprivation_2025 (33,755). council_agenda_items (677). council_pledges.

Candidates speaking for themselves

candidate_invitations (token hash, channel, status) and candidate_submissions (statement, source, check, resulting claim). View invitation_status.

Automatic lines, job log and watches

school_changes, council_consultations, gazette_notices, local_plans (replaced wholesale by their jobs). job_runs (every run), source_checks (each re-reading of a source), feed_items, release_watch. Plus candidates.withdrawn_at and sources.archive_url.

Counts, never people

usage_totals (lookups per ballot per day), feedback_totals (daily answer counts), feedback_comments (no identifiers). resources: further-reading links.

06 · The heart of it

The claims ledger

Everything the site says about a party or candidate is a row in one ledger. Rows are never changed, only superseded, and every change is public. That is what lets the site say “no way for figures to be manipulated” and mean it.

Figure 2. A claim’s life. Nothing reaches a page except through the ledger.

What a claim holds

  • The quotation (source_quote): verbatim, the record.
  • The summary (claim_text): neutral verbs (“says”, “pledged”, “states”), never “admits”, “boasts”, “fails to”.
  • Who: a party (party_ec_id) and/or one ballot and candidate.
  • Topic: one of nine. One claim per commitment; never bundled.
  • Conditions in applies_if (for example renters, or students), never in the summary. The household profile is matched against these to put the most relevant first; it never hides anything.
  • Re-read every week by the source watch (section 9), with an Internet Archive copy linked as “Archived copy”. Its first pass re-sourced 24 Liberal Democrat claims to where the words actually are.
  • Sources, primary first: the party’s or candidate’s own publication, the official record, the statute; a press report only as a flagged interim. The source’s own date and our retrieval date are both shown.
  • Precision: the threshold rule. A summary may not say “more”, “cut”, “boost”, “invest” without the number, date or object from the source. If the source is vague, it is filed as an aspiration and labelled so.

07 · What it means for you

The money layer

Where a party’s tax or benefit promise is specific enough to model, the site shows what it would change for a household like the visitor’s. The sums are done once, offline, by PolicyEngine UK, and stored as a table the pages look up. Nothing is calculated live.

8,100household cells: 6 age × 6 income × 3 household × 3 children × 5 housing × 5 work bands
5reform sets: 2026 baseline, 2024 baseline, and three party policies
2.98.0PolicyEngine UK version, stored with every row; computed 18 September 2026
Reform setWhat it models
baselineCurrent law, 2026.
baseline-2024Law as it stood for the 2024 comparison.
PP52-2024-employee-ni-6pctConservative 2024: employee National Insurance at 6%.
PP63-2024-ni-upper-earnings-limitGreen 2024: change to the National Insurance upper earnings limit.
PP7931-2026-09-personal-allowance-15000Reform UK, September 2026: personal allowance of £15,000.

The assumptions, stated on every calculation

  • Income at the band midpoint (over £100k uses £130,000), split 60/40 between adults in a couple. Employed means employment income; self-employed, self-employment income; retired, private pension income.
  • Representative ages per band: 17, 21, 30, 42, 57, 70. Children: one child aged 3 (under 5) or 10 (school age).
  • Rent: private £15,600 a year for a single adult without children, £21,600 otherwise; social £9,000; owners £0 (mortgage interest not modelled).
  • The household is assumed to claim Universal Credit and Child Benefit if entitled. Student status has no modelled effect; “other” households are modelled as one adult.
  • Region is London, because the first covered ballot is in London. This must be extended before money figures are shown for ballots elsewhere.
How a household finds its row

lib/household.ts folds the fuller set of profile answers into the grid’s bands (gridKey). The newer answers map onto existing bands: housemates or halls count as “other” households, university halls as “other” housing, a full-time student as “not working”, and studying with a part-time job as “employed”. Unit tests cover the matcher and the key (npm test, 22 passing).

To recompute the baseline: python scripts/compute_grid.py writes batches to scripts/sql/; for a past year, GRID_YEAR=2024 writes scripts/sql-2024/. Party policies are defined in scripts/reform_sets.py and computed by scripts/compute_reform_sets.py. Recompute whenever PolicyEngine changes version or a reform set is added, and record the checksum.

08 · Where you live

Councils and wider bodies

Romily’s round-six idea: make councils a major data set, under “What’s happening where you live”. A council gets its own page, separate from any parliamentary ballot, and every layer of government between council and Westminster is shown as a layer, elected bodies first.

The council page, /council/[slug]

  1. Five topics in fixed order (housing, transport, council tax, environment, education), each quoted from the council’s own publication with link and date. “Nothing found” is said plainly and means nothing found, not nothing happening. District councils say schools belong to the county; counties say housing numbers belong to the districts. Drafts, estimates and government minimums are labelled as such.
  2. What the council is deciding: every Full Council and Cabinet agenda item from about six months back to three ahead, as the council titled it. Motions are labelled with whoever the agenda names as proposer. A party is added only when the name matches exactly one serving councillor.
  3. Who runs the council: control and seats by party, next scheduled election, every councillor by ward, and a link to the register of interests (linked, never summarised). No attendance and no allowances, anywhere.

Where the facts live

Council facts are in lib/councils.json, in git rather than the ledger, so every change is a reviewable diff. 29 councils as of 25 September, gathered by hand from each council’s site. Council tax Band D comes from MHCLG; control and councillors from Open Council Data.

Matching names

Council names are matched exactly after stripping “Borough”, “District”, “City”, “County”, “Council”. A prefix match was removed on 25 September because it gave Aberdeen City the councillors of Aberdeenshire.

Wider bodies

lib/widerBodies.json holds ONS lookups: council to combined authority (106 councils, with mayor flags), the GLA (33 boroughs), and council to fire authority (318). Elected layers (GLA, mayoral combined authorities, Senedd, Scottish Parliament, NI Assembly) join the representatives list. Unelected bodies (NHS integrated care boards, fire and rescue authorities, mayor-less combined authorities, national parks) sit behind “Who else runs things here”, tagged “Not elected”.

09 · Keeping it current

Keeping the data current

A machine refreshes anything that comes from an official register or API, and notices anything else changing. It never rewrites a quotation: a claim is only corrected by a person, as a new superseding row. Full detail is in docs/data-freshness.md.

The source watch

For each of the 232 sources the site quotes, it fetches the page, PDF or Word file, checks every quotation is still present word for word (ignoring case, punctuation and line breaks), records a fingerprint of the text, and keeps an Internet Archive copy: a capture from the last six months if the Archive holds one, otherwise a new one (up to 15 a run, 25 seconds apart). PDFs are read with poppler’s pdftotext, which keeps words whole. A page with almost no readable text (built by JavaScript, or text inside an image) is reported as “check by hand”, not as a missing quotation. Each run is capped at about 35 minutes and takes the least recently checked sources first.

How failures reach a person

  • Every job writes a row to job_runs; /status shows each job’s last run and flags failed or overdue ones.
  • A failed step does not stop the others, but the workflow is marked failed at the end, so GitHub emails the maintainer.
  • Each Monday weekly_review.py opens one GitHub issue, “Weekly data review” (label data-review), listing: jobs failed or overdue; quotations not found; unreadable sources; council facts older than 90 days; new party and GOV.UK publications; new dataset editions; elections with missing candidates or positions; withdrawals.

What the meetings reader leaves out

Only mechanical removals, from a public list in the script: section headings; procedural titles (apologies, minutes, declarations of interest, announcements, questions, petitions, appointments, elections of chairs and mayors, forward plans); private items the council withholds; and, following Romily’s rule, anything about attendance or allowances. Nothing is ranked, matched to a ward or chosen by us. Motions are found by the word “motion” in the title or “this council notes/believes/resolves” in the text; the proposer comes from the title or text.

11 · Quality

Reliability, privacy and accessibility

The site has to work on polling day, on a cheap phone, for someone who has never used it, without learning anything about them.

Reliability

  • Every server-side call to an outside service gives up after 5–8 seconds, so a slow upstream cannot hold a page past the host’s limit and turn it into an error. Each panel already falls back to showing nothing for itself.
  • The boundary and image routes answer 504 on a timeout instead of hanging.
  • Candidate photos are resized by Netlify’s image CDN, so a 56-pixel face costs kilobytes, not a 900 KB original.
  • /status shows when each data set was last refreshed, lists any election the nightly job missed, and shows every automatic job with its last run: OK, failed or overdue.
  • A failed scheduled job fails its workflow, so GitHub emails the maintainer the same day.
  • scripts/check-ballots.py and /about/accuracy test that postcodes resolve to the right ballot (first report: 20 of 20 for Holborn and St Pancras).

Privacy

  • The postcode is sent once, by POST, used to find the ballot and discarded; only the outward code goes further.
  • Household answers are bands and stay in the browser. Display settings, notes and topic order use browser storage only.
  • What is logged: anonymous daily page counts per election and aggregate bot traffic. No IP addresses, no tracking cookies, no per-visitor records.
  • Forms that take input (household form, submission portal, maintenance console) are excluded from crawlers in robots.txt.

Accessibility

Light and dark themes, text size, a high-contrast mode, a light mode for slow connections, read-aloud and a plain-English toggle. Selected answers carry aria-pressed and are filled with a tick in both themes. A forced-colours rule keeps borders in Windows high-contrast. Every layout was checked for sideways scrolling at 320 pixels, at 320 pixels with 150% text, and at 1920 pixels. Pages are checked with axe (scripts in scripts/a11y/); the most recent smoke run, across 32 pages, found no violations.

Colour, as a rule

The interface is warm neutrals with one accent, a signature magenta (#D6006F) chosen because no UK party uses it; it marks interface, never identity. Map legend colours must be clearly different from each other and clearly not party colours, and each legend item explains what it means.

Runbooks

The routines, in order. Each assumes you are in ~/code/voter-app on the Mac with a clean working copy.

Add or correct claims

# 3. Commit and push. "Load drafted claims" runs and loads it.

# A correction is a new claim with "supersedes": <old id> and the reason.

Every Monday: the weekly review (about 30 minutes)

  1. Open the issue “Weekly data review”; fix anything under Jobs first.
  2. Quotations not found: open the source and the archived copy. If the words moved, add a superseding claim pointing at where they now are. If they were removed, withdraw the claim in /review with the reason.
  3. Could not be read: open each by hand; replace moved links.
  4. New publications: read each; draft a claim from the exact words where one states a position on a topic. Check Reform UK’s site by hand.
  5. New editions: reload the table named. Facts due: update lib/councils.json.
  6. Close the issue with a note of what was done.

Add a council page

  1. Add an entry to lib/councils.json: slug, name, GSS code, site, system, the six links (plan, budget, meetings, councillors, interests, consultations), and five facts with summary, verbatim quote, URL, publisher, date and a note. Keep “nothing found” entries, with where you looked.
  2. If the council runs Modern.gov and …/mgWebService.asmx/GetCommittees?lDummy=0 answers, add it to COUNCILS in scripts/fetch_council_meetings.py. If its Full Council is listed under the council’s own name, add it to EXTRA_BODIES.
  3. Commit and push (the script change triggers the meetings job), check council_agenda_items, then deploy.

Before a polling day

  1. Check deadlines on the ballot page against Democracy Club’s timetable and the working-day rules.
  2. Run the ballot accuracy check and read /status.
  3. Download /ledger/snapshot and commit it to snapshots/ with its SHA-256.
  4. Freeze deploys unless something is broken.

14 · Why things are as they are

The research library

Ten papers in docs/research/, each fact-checked by a second pass that re-opened the sources. None ranks a candidate or party, and none picks an option for Romily or Barny.

#PaperWhat it found
01Opening lineNeutral tools open with a plain task; small wording changes rarely change behaviour. Four lines compared, none picked.
02Promises against recordsOf 50 pledges from the 2024 manifestos: 5 clean pledge-vote pairs, 7 ambiguous, 38 never voted on.
03The empty record sectionThree patterns in use elsewhere; four layouts set out. Romily chose option 4.
04CouncillorsEnglish councils must record names on budget and council tax votes (since 2014); otherwise no dataset of council votes exists.
05The regional levelNo single regional level; what sits between council and Westminster varies by postcode. The site needs its own tables.
06Local-issues ruleMost councils tested run Modern.gov with an open web service; a draft rule tried on one ward.
07Running costsThe shared Netlify pot runs out monthly; costs set out for four hosts under stated assumptions.
08Track-record sourcesCommons Votes API, TheyWorkForYou, Modern.gov, ElectionLeaflets, planning.data.gov.uk tested.
09Sources behind two dashboardsLocal Intelligence Hub and the Constituency Dashboards aggregate about 60 official datasets we don’t yet use, mostly OGL, all by constituency.
10Promises, every methodOnly Bill Royal Assent dates and numbered money pledges stay pure fact: 18 of 25 Labour 2024 commitments checked have Royal Assent, 3 are in progress, 4 have no Bill.

Raw SQL must cast to these types, for example 'housing_and_property'::topic, or Postgres refuses the insert. Supabase’s SQL runner returns only the last statement’s result, so run one statement per query when checking.

Terms

applies_ifA claim’s conditions in structured form (for example renters), matched against the household profile to order what is most relevant first. It never hides a claim.
ballot_paper_idDemocracy Club’s id for one ballot paper, for example parl.holborn-and-st-pancras.by.2026-10-08.
CMISA council meetings system with no open web service like Modern.gov’s.
current_claimsThe view of live claims: not superseded, not withdrawn.
EC idElectoral Commission party registration number, for example PP52.
GSS codeThe ONS code for an area (E09000007 is Camden).
LayerThe kind of source a claim comes from: manifesto, enacted record, candidate statement, campaign leaflet, third-party analysis.
Modern.govThe meetings system most councils use; many expose a public web service (mgWebService.asmx).
OGLOpen Government Licence, under which most official statistics are published.
PolicyEngine UKAn open-source tax-and-benefit model of the UK, used offline to compute the receipt grid.
PrecisionMeasurable (a number, date or object) or aspiration (“Stated aim, no measurable commitment found”).

Service roleThe Supabase key that can write. Held only in Netlify, GitHub secrets and by Barny.
SoPNStatement of Persons Nominated: the official list of candidates on a ballot.
